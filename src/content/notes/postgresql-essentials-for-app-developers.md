These are the PostgreSQL basics I need before writing any Python against it: how to run it, how to get around in psql, how it organises things, and how to design a schema that rejects bad data by itself. The running example is the inventory API project: warehouses that hold items.

## Running Postgres 18 in Docker

```sh
docker volume create pgdata
docker run -d --name pg \
  -e POSTGRES_USER=inventory \
  -e POSTGRES_PASSWORD=inventory \
  -e POSTGRES_DB=inventory \
  -p 127.0.0.1:5432:5432 \
  -v pgdata:/var/lib/postgresql \
  postgres:18
```

- `POSTGRES_PASSWORD` is required. `POSTGRES_USER` creates a superuser and `POSTGRES_DB` the first database.
- From version 18 the image keeps its data in a version-specific directory (`/var/lib/postgresql/18/docker`) and the volume belongs at `/var/lib/postgresql`. Older tutorials mount `/var/lib/postgresql/data`; with 18 the container refuses to start and prints an error explaining the new layout. The version in the path is deliberate: it makes major-version upgrades with `pg_upgrade` possible inside one volume.
- Binding to `127.0.0.1` keeps the database off the local network.
- Scripts in `/docker-entrypoint-initdb.d` only run when the data directory is empty. Changing them later does nothing to an existing volume.

## Getting around in psql

```sh
docker exec -it pg psql -U inventory -d inventory
```

Meta-commands start with a backslash and are handled by psql itself; anything else is SQL and needs a terminating `;`.

| Command | What it does |
| --- | --- |
| `\l` | list databases |
| `\c dbname` | connect to another database |
| `\dn` | list schemas |
| `\dt` | list tables in the search path |
| `\d item` | describe a table, its indexes and constraints |
| `\du` | list roles |
| `\x auto` | expanded output for wide rows |
| `\timing` | show how long each statement took |
| `\conninfo` | which database, user and host I am on |
| `\q` | quit |

## How Postgres organises things

- A **cluster** is one running server. It holds several **databases**, and a connection is always to exactly one database; there are no cross-database queries.
- Inside a database, **schemas** are namespaces for tables. `public` exists by default. Since Postgres 15, ordinary roles can no longer create objects in `public` unless they own the database or are granted `CREATE`.
- **Roles** are both users and groups. A "user" is just a role with `LOGIN`.

Coming from Oracle, the main mental shift is that an Oracle schema is tied to a user, whereas a Postgres schema is just a namespace that a role may or may not own.

```sql
CREATE ROLE inventory_app LOGIN PASSWORD 'change-me';
GRANT CONNECT ON DATABASE inventory TO inventory_app;
GRANT USAGE ON SCHEMA public TO inventory_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO inventory_app;
```

`ON ALL TABLES` only covers tables that exist right now. For tables that future migrations create, the owning role also needs `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO inventory_app;`.

## Types worth choosing deliberately

| Need | Use | Avoid |
| --- | --- | --- |
| Surrogate key | `integer` or `bigint GENERATED ... AS IDENTITY` | `serial` (legacy) |
| Money | `numeric(10, 2)` | `real`, `double precision`, `money` |
| A point in time | `timestamptz` | `timestamp` (no time zone) |
| Text | `text`, or `varchar(n)` when the limit is a real rule | `char(n)` |
| Public identifiers | `uuid`, generated with `uuidv7()` (new in 18) | exposing sequential ids |
| Semi-structured attributes | `jsonb` | `json` (keeps whitespace, no indexing) |

`timestamptz` does not store a time zone: it stores an absolute instant (in UTC) and converts on the way out using the session's `TimeZone` setting. Plain `timestamp` is a wall-clock reading with no zone, which is almost never what an application means. Floats cannot represent `0.10` exactly, so money must be `numeric`; in Python it arrives as `decimal.Decimal`.

`text` and `varchar(n)` are stored the same way; the length is only a constraint.

## The inventory schema

```sql
CREATE TABLE warehouse (
    id   integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name varchar(100) NOT NULL UNIQUE
);

CREATE TABLE item (
    id           integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    warehouse_id integer NOT NULL REFERENCES warehouse (id) ON DELETE CASCADE,
    sku          varchar(32) NOT NULL UNIQUE,
    name         varchar(200) NOT NULL,
    quantity     integer NOT NULL DEFAULT 0 CHECK (quantity >= 0),
    price        numeric(10, 2) NOT NULL,
    description  text,
    created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX item_warehouse_id_idx ON item (warehouse_id);
```

Why each piece is there:

- **NOT NULL** by default. A nullable column should be a decision (here, only `description`).
- **CHECK (quantity >= 0)** makes negative stock impossible, whatever bug the Python code has.
- **REFERENCES** makes orphan items impossible. `ON DELETE CASCADE` deletes a warehouse's items with it; `RESTRICT` (or the default `NO ACTION`) would refuse instead. That is a business decision, not a technical one.
- **UNIQUE** on `sku` creates an index automatically. Foreign keys do not, hence the explicit index on `warehouse_id`.
- `GENERATED BY DEFAULT AS IDENTITY` is the SQL-standard replacement for `serial`, and it is what SQLAlchemy emits for `Identity()`. `GENERATED ALWAYS` would also reject explicit ids.

Normalisation keeps facts in one place: the warehouse name lives in `warehouse`, not copied into every item. A `jsonb` column is fine for genuinely open-ended attributes (say, supplier-specific metadata), but anything I filter, join or constrain on deserves a real column.

## Two statements I will use constantly

```sql
-- Get generated values back without a second query
INSERT INTO warehouse (name) VALUES ('London') RETURNING id;

-- Upsert: insert or add to the existing quantity
INSERT INTO item (warehouse_id, sku, name, quantity, price)
VALUES (1, 'BOLT-M6', 'M6 bolt', 100, 0.12)
ON CONFLICT (sku) DO UPDATE
SET quantity = item.quantity + EXCLUDED.quantity
RETURNING id, quantity;
```

`EXCLUDED` is the row that failed to insert. `ON CONFLICT` needs a unique index or constraint matching the conflict target.

## Gotchas

- **DDL is transactional.** Unlike Oracle, `CREATE TABLE` or `ALTER TABLE` inside `BEGIN ... ROLLBACK` really is rolled back. Good for migrations, surprising if I expect an implicit commit.
- **Empty string is not NULL.** Oracle treats `''` as `NULL`; Postgres does not. Add `CHECK (name <> '')` if empty names are invalid.
- **Unquoted identifiers are folded to lower case.** `CREATE TABLE Item` creates `item`. Quoting (`"Item"`) makes the name case-sensitive forever, so I never quote.
- **Deleting the container is fine; deleting the volume is not.** `docker rm pg` keeps data in `pgdata`; `docker volume rm pgdata` or `docker compose down -v` is permanent.
- **`localhost` inside a container is the container.** Another container reaches Postgres by service or container name on a shared network, which the Docker Compose note covers.
